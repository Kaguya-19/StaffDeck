# SD browser approval consumer fixed increment

The adapter-owned `frontend-enterprise/src/pages/chat/PilotDeckApprovalInboxConsumer.tsx` exports `PilotDeckApprovalInboxConsumer` and `usePilotDeckApprovalInbox`. The root may wrap either existing `ChatPage` or `ChatGalleryPage` with `PilotDeckApprovalInboxConsumer({Page,mapping,refreshKey?,onPrepared?,onError?})`; the wrapper injects `{status,loading,submitting,error,onReply}` into their existing `pilotDeckApprovalInbox` prop. It does not edit canonical `FormalSopApprovalInbox`, native handoffs or either ChatPage.

`mapping:{sessionKey,projectKey?}|null` must come from the original authenticated SD→PD admission record. `chat.sessionId` and `ExternalSessionBinding.external_session_id` are not substitutes. Null mapping makes zero calls, reports `SOP_APPROVAL_SESSION_MAPPING_UNAVAILABLE`, and offers no pinned reply. Normal SD `api` reads the logged-in approver token for GET `/api/v1/pilotdeck/approvals/{session_key}` and POST `/api/v1/pilotdeck/approvals/reply`; the service bridge credential remains server-only. Reply body is exactly `{session_key,request_id,wait_id,expected_revision,message}`. The adapter retains one request ID for a failed same-command retry, checks the original pinned wait/revision and receipt, refreshes after success, and aborts request-local work on scope change/unmount. It does not prefetch pending wait or keep a second wait store.

This is a consumer to be integrated after the public router, PD bridge and admitted-session resolver are installed by their existing owners. Focused 2/2 browser tests pass. The full SD typecheck in this isolated UI-owner base reports only pre-existing business-UI test export errors outside this increment; it reports no error in the new adapter file. No live approval or G gate is claimed.
